# BC250 DX12 pipeline caching and shader investigation

These tools replace the experimental Vulkan Lite optimization tools. They operate
on OptiScaler's directly selected AMD DX12 upscaler provider, `amdxcffx64.dll`,
on the real BC250 adapter (`1002:13fe`). They also apply when a Vulkan game uses
OptiScaler's DX12 upscaler backend. They do not wrap a native Vulkan upscaler or
the game's other shaders, and do not replace either AMD DLL.

## Controls and defaults

Select the AMD driver FSR entry in the DX12 upscaler list. The **BC250 DX12 tools**
controls appear independently of the **FSR4 Model** selector. They remain visible
but disabled when another provider is selected, explaining which backend is needed.

- **Cache DX12 FSR pipelines** defaults to enabled on BC250. Disabling it recreates
  the upscaler using the original creation path. Use **Save Settings** to persist.
- **Capture DX12 FSR shaders** defaults to disabled. Enable only for investigation,
  then disable before timing runs. It also recreates the upscaler.
- Session counters show plain compilations, accepted cached blobs, rejections and
  bypassed calls. No observed calls means there is no evidence these tools have
  participated. A bypass is not a cache hit.

The INI keys under `[FSR]` are:

```ini
Fsr4Dx12PipelineCache=true
Fsr4Dx12ShaderCapture=false
```

The cache works independently of model-discovery hooks. It does not select Lite,
change neural weights, change quality presets, or enable frame generation. The
existing BC250 model defaults and explicit overrides are preserved. Model support
and actual output still need checking in the overlay and log.

## What caching does

The implementation observes synchronous compute-pipeline creation while OptiScaler
creates or dispatches the AMD provider's upscaler contexts. It covers both
`ID3D12Device::CreateComputePipelineState` and ordinary compute streams passed to
`ID3D12Device2::CreatePipelineState`. Background worker threads, external providers
called outside these wrappers, and pipeline-library loads are not intercepted.

Successful creations can supply `GetCachedBlob()` data for a subsequent creation.
Files live under `OptiDllPath/BC250Dx12/cache/`. The SHA256 identity includes adapter
IDs, adapter LUID, the reported driver version, exact shader bytes, the digest of
the root-signature creation bytes, node mask and pipeline flags. Root identities
are object-owned private data; no pipeline or root-signature COM objects are retained.
A null root signature is keyed together with the shader's embedded signature.
An explicit root signature whose creation was not observed bypasses caching.

Cache files have a versioned header, matching identity, payload length and corruption
checksum. Reads are limited to 64 MiB per blob. Writes use unique temporary files
and atomic replacing renames. Failed reads/writes keep the ordinary creation path.
Existing provider-supplied cache data, validation-only calls, unrecognized interfaces,
and unknown or mixed graphics pipeline streams are passed through unchanged.

D3D12 remains the authority on blob compatibility. Adapter or driver mismatch and
`E_INVALIDARG` trigger one retry with the exact original descriptor. Device removal,
out-of-memory and other errors are returned without an extra attempt. When DXGI
does not report a driver version, this is logged and compatibility relies on this
runtime validation. Stale or corrupt files are replaced after a successful normal
creation. Cached-blob acceptance does not prove the backend avoided all compilation.

This targets repeated compilation, context creation and related stutter. It does
not reduce per-frame GPU inference work. VKD3D-Proton, Mesa and Steam may already
cache the relevant work, so the incremental benefit requires measurement. Keep
existing system caches and game settings fixed, compare this option off versus
first enabled creation versus a repeated launch, and record startup time, first-use
stutter and steady-state frame times separately. Logging reports host time spent
inside pipeline-creation calls, not shader execution time.

To reset only these tools, stop the game and remove `OptiScaler/BC250Dx12/`. The
normal OptiScaler remover deletes this directory with the rest of the runtime.

## Shader investigation and the sibling driver's findings

Capture writes unchanged DXIL containers (`.dxil`), root-signature creation blobs
(`.rootsig`) and pipeline metadata (`.json`) into `OptiDllPath/BC250Dx12/capture/`.
Metadata records pipeline flags, node mask, shader size and the model reported by
the provider support checks. That report is not independent verification of GPU
output. If a root signature was not observed, metadata says so and caching skips
that pipeline; its shader can still be captured. Shader capture does not transform
or replace bytecode. Standard DXC disassembly tools can inspect the captures.

The sibling `bc250-fsr4` investigation (`IMPLEMENTATION-NOTE.md` and
`BC250-LITE-DRIVER-INVESTIGATION.md`, local uncommitted notes reviewed 2026-10-25)
places the measured throughput work in RADV's SPIR-V → NIR → ACO compiler path:
signed-dot lowering, optimizer ordering, register pressure, spills and occupancy.
DX12 games reach that path through VKD3D-Proton when it uses the patched RADV driver.
Those driver techniques therefore do not require a separate OptiScaler DX12 port.
Keep the sibling driver's ICD selection in the game's launch options.

The notes specifically warn against blindly expanding signed packed dots: doing so
can erase the deferred-lowering opportunity and worsen spills. No DXIL rewrite,
native signed-dot enablement, FP8 capability change, altered weights or faster shader
replacement is shipped here. The older Vulkan shader tool and override switches
are removed rather than repurposed for a different API.

For a throughput experiment, use a DX12 game such as Cyberpunk 2077 or Resident Evil
Requiem with the same model, resolution and scene. Correlate the captured DXIL with
VKD3D/RADV's translated shaders and final ISA. Measure GPU pass time, VGPRs, spills,
scratch, LDS and occupancy before choosing a transformation. Full-model V3 shader
counts and results do not establish the right thresholds or benefits for Lite.

## Checks

`python3 tests/test_bc250_dx12_cache.py` compiles the production cache storage,
retry policy and compute-stream parser on the host. CI repeats it against the
real Windows SDK before building the DLL. These tests do not establish a BC250
speedup or replace a Windows build and hardware image/frame-time comparison.
